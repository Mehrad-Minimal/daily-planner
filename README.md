# Daily Planner

A minimal, iOS-style daily planner with email sign-in. Each person's tasks are stored in Cloud Firestore, so plans follow you across devices.

> **Generated by Claude Sonnet 5.5.** This project, including the app code, the database schema, and this README, was written by Claude Sonnet 5.5, an AI model made by Anthropic, in a conversation with a human who directed the design and requirements. Review it before relying on it.

## Features

- Large-title layout, week strip with a spring-animated day selector, and a progress ring for the day
- Add tasks with an optional time and a color
- Tap to complete (animated checkmark and strike-through), swipe left to delete
- All / To do / Done filter
- Email and password accounts through Firebase Authentication, with password reset by email
- Tasks saved per user in Firestore, with security rules so nobody can read or change another person's data
- Changes appear live on every open device
- Keyboard support: Enter or Space toggles a focused task, Delete removes it
- The day rolls over automatically at midnight, even if the tab stays open
- Light and dark mode that follow the device setting
- Reduced-motion support

## How it works

The app is a static site with no build step. `public/index.html` contains the interface and logic. It loads the Firebase SDK as ES modules from Google's CDN, pinned to a specific version.

| Piece | Where |
| --- | --- |
| App (HTML, CSS, JS) | `public/index.html` |
| Firebase web config | `public/config.js` |
| Firestore security rules | `firestore.rules` (deployed with the Firebase CLI) |
| Netlify settings and security headers | `netlify.toml` |

Data model: each task is a document at `users/{uid}/tasks/{taskId}` with the fields `title`, `day` (`YYYY-MM-DD`), `time` (`HH:MM` or null), `color`, and `done`. The app listens to the visible week, so edits from another device appear without a refresh.

## Security notes

- `config.js` contains the Firebase **web** config. It identifies your project and is designed to be public. Protection comes from `firestore.rules` and from the Authentication settings, so keep the rules deployed.
- Never put a Firebase Admin SDK service account key in this repository or in browser code.
- `netlify.toml` sets a Content-Security-Policy that allows scripts only from Google's CDN and connections only to Google APIs, plus framing protection.

## Set up your own copy

1. **Create a Firebase project** at console.firebase.google.com, using Add project.
2. **Enable email sign-in.** Go to Build → Authentication → Get started → Sign-in method, and enable **Email/Password**.
3. **Authorize your domains.** In Authentication → Settings → Authorized domains, add your Netlify address (for example `your-site.netlify.app`). `localhost` is already listed for local testing.
4. **Create the database.** Go to Build → Firestore Database → Create database. Choose a region (it can't be changed later) and start in production mode.
5. **Add your config.** In Project settings → General → Your apps, add a Web app. Copy the `firebaseConfig` values into `public/config.js`.
6. **Deploy the security rules.**
   ```bash
   npm i -g firebase-tools
   firebase login
   firebase use --add        # choose your project
   firebase deploy --only firestore:rules
   ```
7. **Run locally** with any static server, for example `npx serve public`.

## Deploy to Netlify

Option A, continuous deployment: push this repository to GitHub, then in Netlify choose Add new project, Import an existing project, and select the repo. `netlify.toml` already sets the publish directory to `public`, and no build command is needed.

Option B, CLI:

```bash
npm i -g netlify-cli
netlify deploy --prod --dir=public
```

If you link a site with the CLI, keep `.netlify` out of git. It is already in `.gitignore`.

## Notes and limits

- Passwords need at least 8 characters when you create an account. Firebase itself accepts 6, but the app enforces 8.
- Password reset emails open a page hosted by Firebase, where the user chooses a new password, then they sign in as usual.
- Email verification is sent when an account is created, but it is not required to use the app.
- Tasks are not shared between accounts. Tasks can be checked off or deleted but not edited yet; delete and re-add one to change it.
- Changes made while offline are queued and sent when the connection returns, as long as the page stays open. They are not saved across a page reload while offline.
- Existing Supabase accounts and tasks do not move automatically. Users need to create an account in the new project.
